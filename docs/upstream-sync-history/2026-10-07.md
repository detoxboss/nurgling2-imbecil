## Database architecture: fork migrations leave upstream's version sequence

Third collision in three cycles was imminent: the fork took positive 13 (vs upstream's
`quest_shares` 13), was renumbered to 15 (vs upstream's `forage_finds` 15). A version-16 bridge
would have scheduled the next one and, by raising shared `MAX(schema_version)` to 16, would have made
every released v1.0.9 client throw `SchemaTooNewException`.

**Chosen instead: a separate fork-owned ledger.**

```
schema_version          UPSTREAM migration namespace. Positive only. Fork-specific migrations
                        never claim or advance it; upstream's own migrations still record here.
  13 = quest_shares   14 = timers   15 = forage_finds
  CLIENT_MAX_SCHEMA_VERSION = 15   (tracks UPSTREAM's highest migration, nothing else)

fork_schema_migrations  FORK-ONLY migration namespace, keyed by stable descriptive string id
  0001-stack-sizes-lineage-bridge
```

The invariant is **fork-specific migrations never claim or advance the upstream-owned positive
`schema_version` namespace** — not that the merged client never writes that table. It still runs
upstream's numbered migrations and records each of them there, which is exactly what that table is
for. `ForkMigrationManager` itself writes only to `fork_schema_migrations`.

`src/nurgling/db/migration/ForkMigrationManager.java` (new) owns it. `DatabaseManager` runs
upstream's pass, then the fork's, then `loadSchemaSnapshot()`.

A negative-ID scheme inside `schema_version` was analysed in Phase 1 and rejected in favour of this:
it reuses an upstream-owned column with changed semantics, and `runMigrations()`'s
`migration.version > currentVersion` loop cannot run a negative id anyway, so it needed a separate
runner regardless. The separate table costs one extra DDL and gains unlimited, self-documenting
headroom. Its one real risk — a restricted role that cannot create the bookkeeping table — is tested
and handled (below).

**Intersection with `MigrationManager` was reduced, not increased.** ~150 lines of fork-only code
(`createStackSizesTable`, `seedStackSizes`, `reconcileStackSizes`) moved **out** of that
upstream-owned file into `ForkMigrationManager`, along with the fork's migration entry and constant.
What remains fork-facing there is six package-visible helpers the fork reuses so no DDL exists twice:
`createQuestSharesTable`, `createTimersTable`, the newly extracted `createForageFindsTable`
(idempotent internally, called by both upstream's migration 15 and the fork bridge),
`createTable`, `grantDml`, `safeCreateIndex`, plus `isAlreadyExists`.

### Transitional v1.0.9 lineage — the case this exists for

A released v1.0.9 database already reads positive version 15, so `runMigrations()` will **never** run
upstream's migration 15 on it again and `forage_finds` would stay missing forever — the identical
trap the 13→15 bridge was built for, one number later. The fork bridge therefore also ensures
`forage_finds`, reusing upstream's creator. Proven on both back ends: upstream's pass is a verified
no-op on that fixture, `forage_finds` is still absent after it, and the fork pass creates it while
`MAX(schema_version)` stays exactly 15 and `stack_sizes` rows are preserved.

### Failure semantics

Every fork migration is optional by construction. A `SQLException` anywhere inside one propagates:
`runForkMigrations()` rolls back, records **nothing**, reports it in a `Map<String,String>`, stops
later fork migrations so a success cannot mask the failure, and retries next start. No per-step
try/catch — the same reasoning as the old migration 15: swallowing per step could record success with
a structure missing, and on PostgreSQL would continue inside an aborted transaction.

If the ledger table itself cannot be created or read (restricted role), **no fork migration is
attempted at all** — there would be no way to record success, and in practice such a role cannot
create the fork tables either. All fork migrations are reported skipped, nothing is stamped, existing
fork tables stay usable through `DatabaseManager.tableUsable(...)`, and the attempt repeats.

### Standing rule (new)

Fork database extensions are additive and isolated: new fork-only objects take a `fork_`/`h4d_`
prefix and a fork ledger migration with a stable string id; upstream-owned tables do not get their
semantics changed without a compelling compatibility reason. `stack_sizes` keeps its unprefixed name
deliberately — released clients already read and write it. Recorded in
`docs/fork-customization-ledger.md`, "Fork database extensions: additive, isolated, own ledger".

## ExploredArea: fork ownership + upstream's async writer

Taken from upstream: `saveAsync()` on a dedicated single-thread `exploration-save` executor;
`mergeAndSaveToFile()`'s `tryLock` → one `LOCK_RETRY_SLEEP_MS` retry → refuse rather than clobber;
the `dataEpoch` recheck that preserves exploration discovered *during* a save; immutable per-grid mask
snapshots.

Kept from the fork, and now built on top of that writer rather than beside it: per-instance
`needSave`/`lastChangeTime`/`revision`/`pendingSave`/`pendingRevision`/`nextAttemptAt`/`failures`,
all under one `saveLock`; the trigger is this session's own `NCore.tick()` → `saveIfDue()`.

Three properties the raw auto-merge did **not** have:

1. **Saves are actually asynchronous again.** After the `NConfig` deletion, upstream's `saveAsync`
   had zero callers and `saveIfDue()` ran `mergeAndSaveToFile` synchronously on the tick thread —
   reintroducing the frame stall upstream had removed, 100 ms lock sleep included. `saveIfDue()` now
   starts `saveAsync` and returns.
2. **A completed older write cannot clear newer dirty state.** Each save captures `revision`; the
   completion handler clears `needSave` only if `revision` has not moved since.
3. **A busy file backs off.** On failure `needSave` is left set (nothing is lost) and `nextAttemptAt`
   advances by `2000 ms << failures`, capped at 60 s, instead of retrying every tick.

`saveOnTeardown()` (called from `NGameUI.dispose()`, replacing `saveNow()`) waits, because the
executor thread is a daemon and a fire-and-forget write is simply lost on client exit. It
distinguishes three states: nothing dirty → return; a save in flight that covers the current
revision → wait for it and start nothing (a second write would queue behind it and then be refused
the file lock); a save in flight that is now stale → wait, then issue exactly one more. The wait
budget is derived rather than picked — two lock-retry windows (the internal bound on one attempt)
plus a 2 s allowance for the merge and atomic write — and on timeout the dirty flag is **left set**
rather than falsely cleared.

Covered by upstream's own `ant test-exploration-performance` (PASS, including file-lock safety and
profile isolation). Two-session runtime proof is still outstanding — see below.

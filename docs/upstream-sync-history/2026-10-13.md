## Database architecture

**No schema change.** `CLIENT_MAX_SCHEMA_VERSION = 15` at upstream's tip; there is no migration 16;
`MigrationManager`, `ForkMigrationManager` and `DatabaseManager` are byte-identical to `origin/master`.
`fork_schema_migrations` / `0001-stack-sizes-lineage-bridge` are untouched, no positive fork migration
exists, and no `stack_sizes` data is rewritten by this sync.

The new storage recorder uses the existing `containers` and `storageitems` tables. Encodings live in
existing columns (`storageitems.quality` has always been nullable):

- stockpile: one row per item, `quality` NULL, `coordinates` `#pile:<i>`;
- barrel / cistern: one row, `coordinates` `#bulk:<amount> <unit>`, quality possibly NULL.

`StorageItemDao.loadAllStorageItems` now `LEFT JOIN`s `containers` to carry `grid_id`.

**Verified on a disposable SQLite file (scratchpad, not committed; no production or shared database was
touched):** both migration passes run with nothing skipped, `schema_version` MAX is 15 with no rows >15
or <1, null-quality / `#pile:` / `#bulk:` rows insert and round-trip through the real `StorageItemDao`
(pile reads back quality 0 / not bulk / grid joined; bulk parses amount and unit), the re-key SQL of
`moveStoredContainer` moves rows, and replacing with an empty set clears a pile.

**Storage identity.** `NGob.hash` stays write-once (the stable identity: bots, per-instance Gob
Configure); `NGob.storageHash()` is the DB key and is re-keyed when a liftable storage gob is carried and
put down. Gob Configure (`GobCustomize`, `ConfigureGobAction`) has zero `storageHash` references and
still keys off `hash`. Recorded in the ledger ("Gob identity: `NGob.hash` vs `NGob.storageHash()`").

**Stack-size seed.** The static stack seed grows **815 → 816**. Established by running
`StackSupporter.staticSeedSnapshot()` against both VSpec versions: the single added row is
**`Pipestuff`, max 3, stackable** (its `Pipeweed` category is in `categorySize`). No row was removed or
changed, and Wine, Batter, Smokering and Smokeship add no seed rows. Existing databases are unaffected —
`StackSizeService.lookup` returns null for the unseen name and falls back to the static table; the
bridge migration is already recorded and does not re-run; manual and learned rows are untouched.

- **`NUI.keydown` / Squad input ordering** (`src/haven/UI.java` unchanged; `src/nurgling/NUI.java`
  not touched by the fork since merge-base, so this applies with no conflict). Upstream changes
  `NUI.keydown` from `super.keydown(ev)` to an inlined
  `if (!dispatch(root, KeyDownEvent)) { if (!SquadView.key(...)) dispatch(root, GlobKeyEvent); }`.

  - `setmods(ev)` is still called earlier in `NUI.keydown`, outside the changed block — not lost.
  - `SquadView.key()` returns `false` immediately unless `Squad.commander()` is on for that
    session and the UI is the active one, so Commander-off behavior is provably unchanged.
  - FocusGuard's own toggle hotkey and `intercept()` gate live in `NGameUI.keydown(KeyDownEvent)`

    before `SquadView.key()` is ever reached. When the guard's `intercept()` lets a key fall
    through (`ev.stop(); return false`, "so normal hotkeys get the key" per its own comment),
    that fallthrough now reaches `SquadView.key()` before `GlobKeyEvent`/combat-belt — consistent
    with upstream's stated intent ("[squad keys] must win over fight and belt keys, but never over
    a text field") and not a change to what FocusGuard itself gates.

    genuinely focused text field still absorbs the keystroke untouched.

## Multi-session lifecycle supplement (commit `e3281877d` + related: `0caaf4ecb`, `8ee8add28`)

Traced from source, not from the commit messages alone (messages quoted only where they match what
the diff shows). Inspected ≠ tested — none of this has been exercised at runtime yet.

- **`ChunkNavStore` acquire/release/world-change/last-session-save.** `ChunkNavStore` is a new,
  package-private, static, per-genus (per-world) singleton registry (`stores: Map<String,
  ChunkNavStore>`) with a manual refcount (`refs`), not GC-managed: `acquire(genus)` creates-or-
  reuses and increments; `release(store)` decrements and only on reaching zero removes it from the
  map and calls `save()`. `ChunkNavManager.initialize(genus, ui)` calls `release(oldStore)` before
  `acquire(newGenus)` on a world change, and `shutdown()` stops `recordingExecutor` then calls
  `release(store)`. The call I had to verify by searching the whole target tree rather than one
  file: `shutdown()` is invoked from **`NGameUI.dispose()`** (`if(map instanceof NMapView) {
  nmapView.getChunkNavManager().shutdown(); }`), *not* from `NMapView.dispose()` — `NMapView.
  dispose()` only shuts down `storageTrail`. Grepping every `chunkNavManager.` call site in the
  target tree confirms this is the only `shutdown()`/release path and it is unconditional on
  `NGameUI.dispose()` being reached (no early return precedes it). So: acquire/release/last-save is
  real and closed, not just claimed by the commit message — provided `NGameUI.dispose()` itself
  always runs, which is the fork's own long-standing invariant this sync must preserve (see the
  `focusGuard.reset()`/`onGameUIDisposed(this)` conflict above, both of which precede this call in
  the merged method).
- **Recorder executor ownership and `ThreadLocalUI` binding.** `ChunkNavManager.initialize(genus,
  ui)` stores the owning `NUI` and creates a dedicated single-thread daemon executor
  (`"ChunkNav-Recorder"`). Recording tasks submitted to it are wrapped in a `bound(Runnable)` helper
  that sets `ThreadLocalUI` to the captured session before running and `clear()`s it in a `finally`
  — explicitly to fix an observed bug the commit names (`NUtils.player()` inside the recording task
  was resolving to the *active* session, not this executor's own). The save task submitted during
  `shutdown()` is not wrapped in `bound()`; reading `ChunkNavStore.save()`, it only touches the
  graph and does file I/O, no ambient `NUtils`/ThreadLocalUI-dependent lookups, so the omission
  looks intentional rather than a gap. `recordingExecutor.shutdown()`/`awaitTermination(2s)`/
  `shutdownNow()` fallback in `ChunkNavManager.shutdown()` means the thread is bounded at teardown,
  not just daemon-reaped at JVM exit.
- **Background terrain mesh disposal / foreground regeneration.** Three cooperating pieces, all
  upstream-only (none in the 15 shared-edit paths, so no conflict surface): (1)
  `SessionContext.keepMeshes(boolean)` (new, 12-line addition) toggles `session.glob.map.
  meshes(on)` — called `false` when a session goes headless, and `true` *after* the headless tick
  thread has fully stopped when promoted back to foreground (ordering is explicit in-code: the
  comment notes this avoids the just-stopped headless thread's last tick dropping meshes the
  now-visible session needs). (2) `haven.MapView`'s per-grid cut-tracking `tick()` now checks
  `!map.meshes()` first and, if meshes are off, calls a new `clear()` that removes every tracked
  `RenderTree.Slot` cut and resets `lastload` — i.e. it actively lets go of geometry rather than
  merely skipping new builds. (3) the outer `MapView.tick()` adds `if(!glob.map.meshes())
  glob.map.dropmeshes();` right after the grid tick, freeing the meshes the per-grid `clear()` just
  released cuts on. `NMapView.java`'s one line in this commit is unrelated to meshes (the
  `chunkNavManager.initialize(genus, ui)` signature update, covered above) — the mesh mechanism
  itself lives entirely in base `haven` classes and `SessionContext`, nothing fork-owned to
  reconcile.
- **`BotExecutor` and plugin teardown vs. fork owning-session hooks.** `BotExecutor.java` is
  upstream-only in this delta (not one of the 15 shared paths). The change: every bot/support/task
  thread body now reads `boundUI.gui` *at run time* inside the thread instead of closing over a
  `gui` parameter captured at thread-creation time, and a `STOPPED` message helper (`stopped(NUI,
  String)`) does the same re-read; the stated reason (and visible in the diff) is that a long-
  running bot thread previously pinned a dead `NGameUI` (and its map/gobs/widgets) for its entire
  life once the character it started on had logged out. A new `BotExecutor.runOn(SessionContext,
  name, Action)` lets Squad start an order on a *different* session than the caller's own tick,
  registering the thread with that target session's own `BotsInterruptWidget` (`gui.biw.
  addObserve(t)`) so its own stop control still works — this is the per-session-execution item from
  the incoming-work summary, traced to source. `NPluginManager.onGameUIDisposed(NGameUI)` is new
  (12-line addition) and is exactly the method the `NGameUI.dispose()` conflict resolution wires in
  (`onGameUIDisposed(this)`); it is the only place any plugin gets a per-UI teardown notification
  today, per its own comment ("Never called before, so plugins keeping a per-UI entry held every
  dead UI"). Neither file touches a path the fork's owning-session persistence/cleanup hooks
  (ledger: `NGameUI`/`NCore` lifecycle table) depend on; this is additive, not a rewrite of
  fork-owned teardown logic.
- **Not inspected in this pass**: `8ee8add28` ("Stop dead game UIs and old map grids piling up in
  multi-session runs") and `0caaf4ecb` ("Stop gtick leaking finished renders through per-frame
  ThreadLocals") were read for commit intent only, not traced at the diff level, since neither
  touches a shared-edit path or a ledger-named hook. Flagging rather than claiming coverage.
